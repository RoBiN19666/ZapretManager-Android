# Архитектура

## Процессы

| Процесс | Что делает | Почему отдельный |
| --- | --- | --- |
| основной | UI (Compose), `UpdateManager`, приёмники, `DpiEngine`/`TgProxyController` | — |
| `:native` | `ByeDpiVpnService`, byedpi, tun2socks | byedpi — программа с блокирующим `main()` и без корректной остановки; после `shutdown()` её нельзя запустить повторно, поэтому процесс завершается целиком |
| `:tg` | `TgProxyService`, Go-рантайм MTProto-прокси | рантайм живёт отдельно от UI; сервис перечитывает настройки при старте после переиспользования процесса |

Связь процессов — широковещательные сообщения внутри приложения
(`ACTION_STATE`, `setPackage(...)`, `RECEIVER_NOT_EXPORTED`). Состояние движков
публикуется в `DpiEngine.state` / `TgProxyController.state` (`StateFlow`), UI читает его через
`ZmViewModel`.

## Ускорение соединения

```
VpnService.Builder
  addAddress 10.10.10.10/32, addRoute 0.0.0.0/0
  split tunneling: addDisallowedApplication / addAllowedApplication
        │ establish()
        ▼
   tun fd ──► libhev-socks5-tunnel.so (tun2socks, lwip)
                    │ SOCKS5 127.0.0.1:1080
                    ▼
              libzapretnative.so → byedpi main(argv)
                    │ desync: split / fake TLS / OOB / disorder
                    ▼
                 интернет
```

* Запуск: `ByeDpiVpnService.startEngine()` → `VpnService.Builder.establish()` →
  `Native.startByedpi(argv)` → ожидание SOCKS5-порта (TCP-проба) → `Native.startTunnel(yaml, fd)`.
* Аргументы: `ciadpi --ip 127.0.0.1 --port 1080 <токены стратегии>`, где токены берутся из
  выбранной стратегии или из пользовательских аргументов (`{sni}` подставляется автоматически).
* Остановка: `Native.stopTunnel()` (hev quit) → `Native.stopByedpi()` (`shutdown(server_fd)`) →
  закрытие tun → `Process.killProcess` процесса `:native`.
* Ошибки старта (нет VPN-разрешения, порт занят, byedpi не поднялся) публикуются как
  `EnginePhase.ERROR` с текстом, UI показывает их на «Обзоре».

## Подбор параметров

Два независимых сценария, оба идут на живом туннеле и оба не могут работать одновременно
(`TuningGuard`):

* `StrategyTester` — перебирает готовые стратегии (встроенные, пресеты byedpi, список
  ByeByeDPI, свои) и для каждой поднимает движок, ждёт открытия SOCKS-порта и проверяет
  сервисы;
* `Autotuner` — собирает команду сам: готовые пресеты → базовые техники → комбинации
  лучшей базы → модификаторы → финальная перепроверка трёх лидеров длинными пробами
  (иначе победитель на коротких пробах оказывается случайным). Дубли аргументов не
  тестируются повторно, при равном результате выигрывает более короткая команда.

Что применяется, определяет `Strategies.active(...)`: `customArgs` приоритетнее
выбранной стратегии — ровно так строится командная строка для byedpi. Поэтому карточки
«Текущая стратегия» и диагностика показывают именно действующие аргументы, а не
выбранный пресет, который фактически игнорируется.

Результат запоминается для сети: `NetworkProfiles.rememberTuning()` обновляет профиль
текущей сети (Wi-Fi по SSID, мобильная по оператору, запасной `*`) или создаёт его, а
`NetworkWatcher` при смене сети применяет эти параметры. Ручной ввод аргументов
запоминается той же кнопкой на экране стратегий.

## Telegram-прокси

```
Telegram ──tg://proxy──► 127.0.0.1:1443 (libtgwsproxy.so)
                                 │ маршрут (route_order)
                                 ├─ cf_proxy_ws  → Cloudflare Proxy (WS/80 или WSS/443)
                                 ├─ direct_ws    → kws{dc}.web.telegram.org
                                 └─ tcp_fallback → DC:443
```

* Секрет генерируется в Kotlin (`SecureRandom`, 16 байт → 32 hex) и хранится в настройках.
  Go-рантайм принимает только «сырой» секрет; префиксы `dd`/`ee` добавляются при сборке ссылки.
* Конфигурация рантайма — строка токенов `@route_order=...,@route_cf_proxy_ws=1,...`.
  Важно: при наличии `route_order` рантайм считает политику явной и выключает CF, если не передан
  `@route_cf_proxy_ws=1` — поэтому флаги всех маршрутов передаются всегда.
* Статус читается через `GetMtProtoProxyStatus()` (строка `key=value;...`) и обязательно
  освобождается `FreeString`, иначе утечка. Вызовы идут через JNI-мост в `libzapretnative.so`
  (`dlopen` + `dlsym`): JNA/libffi на Android 15/16 роняла процесс `:tg` без Java-исключения.
* Пул CF-доменов обновляется из `Flowseal/tg-ws-proxy` и применяется двумя путями:
  файл обновляется в фоне, а сам список передаётся Go-рантайму токеном
  `@cf_cached_domains` при следующем запуске (`TgConfig.runtimeTokens`). Живой рантайм
  после старта не трогаем: вызов `SetCachedCFDomains` поверх работающего прокси —
  лишний риск уронить его.

## Проверка живости движков

Движки живут в отдельных процессах, поэтому их состояние может «зависнуть» в UI-процессе
последним широковещательным сообщением, даже если процесс уже умер. Отсюда три уровня проверки:

1. сервис сам следит за нативным движком (`byedpiRunning()`/`tunnelRunning()` раз в 1.5 с);
2. `TgProxyService` раз в ~6 секунд проверяет, что порт реально слушает, и что
   `GetMtProtoProxyStatus()` отвечает; три подряд неудачи — перевод в `ERROR`;
3. `DpiEngine` и `TgProxyController` в главном процессе раз в 5 секунд проверяют порт
   (`core/Ports.kt`) и честно показывают ошибку вместо «работает».

`TgProxyService` дополнительно проверяет порт сразу после запуска рантайма: без этого
интерфейс мог показать «маршрут подтверждён», хотя подключиться было некуда.

## Обновления

| Компонент | Источник | Механизм |
| --- | --- | --- |
| APK менеджера | `RoBiN19666/ZapretManager-Android` releases | GitHub API → проверка версии → загрузка → SHA-256 → `versionCode` → `PackageInstaller` |
| Стратегии | `romanvht/ByeByeDPI` (`app/src/main/assets/proxytest_strategies.list`) | raw-файл по коммиту, парсинг в `Strategy` |
| Списки сайтов | `romanvht/ByeByeDPI` (`proxytest_*.sites`) | raw-файлы в `files/components/sites` |
| CF-домены | `Flowseal/tg-ws-proxy` (`.github/cfproxy-domains.txt`) | raw-файл, применяется при следующем запуске прокси |
| Движки | git-сабмодули | обновляются в репозитории, собираются в APK |

Версии компонентов хранятся в `files/components/meta.json`. Файл правят и `UpdateManager`,
и `CfDomains` (в том числе из процесса `:tg`), поэтому запись идёт через `ComponentMeta`
с общим мьютексом и атомарной заменой — иначе обновление одного компонента затирало
метки времени другого.

## Самообновление APK

1. `GitHub.latestRelease(SELF_REPO)` → сравнение `versionName`.
2. Выбор ассета по ABI (`Build.SUPPORTED_ABIS`), иначе `universal`, иначе первый `*.apk`.
3. Загрузка с прогрессом в `cache/updates`.
4. Проверки: SHA-256 из `*.apk.sha256` (обязателен), `packageName`, совпадение подписи
   с установленным приложением, `versionCode` строго больше текущего.
5. Установка через `PackageInstaller` (системный диалог), при недоступности — `ACTION_VIEW`
   через `FileProvider`.

## Настройки и состояние

`Settings` — синглтон с `StateFlow<AppSettings>` и `SharedPreferences`. Пишут и UI, и сервисы,
поэтому изменение идёт под мьютексом (иначе параллельные правки терялись). Движковые ключи
(стратегия, VPN, Telegram) сохраняются через `commit()` — их читают процессы `:native` и `:tg`;
интерфейсные (тема, акцент, автозапуски) — через `apply()`, чтобы не блокировать главный поток.

`TuningJournal` хранит настройки на время теста стратегий и автоподбора: если процесс убьют
посреди перебора, при следующем запуске вернутся прежние значения.

`LogBus` — кольцевой буфер на 800 строк, экспорт в буфер обмена.

## Безопасность

* Все сетевые запросы — HTTPS, сертификаты проверяются системным хранилищем.
* Секрет MTProto не логируется (в журнал попадает только префикс секрета).
* Секрет MTProto **не входит в резервную копию** и не импортируется из архива; системные
  облачные копии и перенос устройства отключены (`dataExtractionRules`/`fullBackupContent`).
* Архивы резервной копии от более новой версии приложения отклоняются по полю `format`.
* APK обновления проверяются по SHA-256, `versionCode` и совпадению подписи с установленным.
* Разрешение VPN выдаётся пользователем; приложение не является системным VPN по умолчанию.
